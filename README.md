# SPP Web App Starter

Aplikasi ini adalah starter web yang menggunakan Supabase sebagai backend untuk memindahkan sistem SPP desktop lama ke web.

## Struktur

- `index.html` — halaman utama aplikasi
- `styles.css` — styling UI
- `app.js` — logika login, dashboard, data siswa, dan pembayaran
- `config.js` — konfigurasi Supabase (`url` dan `anonKey`)

## Langkah setup

1. Buat project baru di Supabase.
2. Buka SQL Editor dan jalankan `../supabase/001_init_spp_schema.sql`. Jika belum pernah dijalankan, lanjutkan dengan `../supabase/005_legacy_mapping_upgrade.sql` agar kolom sekolah legacy dan tabel transaksi tersedia.
3. Jalankan `./supabase/007_legacy_login_rpc.sql`, lalu `./supabase/008_spp_catalog_settings.sql`, dan terakhir `./supabase/009_spp_school_classes.sql`. Migration `009` membuat pengaturan kelas per sekolah, ID VA sekolah dua digit, konfigurasi prefix bank, serta RPC untuk menyimpan perubahan katalog.
4. Di menu Sekolah, atur lalu simpan ID VA dua digit yang unik untuk semua sekolah aktif. Sekolah tanpa data siswa/transaksi dapat dihapus; sekolah yang sudah dipakai hanya dapat dinonaktifkan. Setelah itu, di menu Bank tambahkan prefix VA angka 5–50 digit dan aktifkan maksimal dua bank. Nomor VA siswa dibentuk dari `prefix bank + ID VA sekolah + ID siswa`.
5. Masukkan URL project dan anon key ke file `config.js`.
6. Buka `index.html` di browser, atau jalankan server lokal seperti:

   python -m http.server 8000

   lalu buka:

   http://localhost:8000

## Catatan

- Login legacy memverifikasi akun melalui RPC `login_mastusr`; browser tidak membaca tabel `mastusr` atau password secara langsung.
- Untuk sistem produksi lebih aman, sebaiknya migrasikan ke auth Supabase dan hapus password plaintext dari tabel legacy.
- Data sekolah dibaca dari `mastsek`, data siswa dari `mastspp`/`mastank`, dan transaksi dari `pembayaran`.
- Jalankan `./supabase/010_student_rules.sql` setelah 009 (backup dulu). Migration ini menyimpan data siswa (baru/naik kelas, no. SPP otomatis, riwayat SPP, log, import CSV) lewat RPC khusus Admin. Data siswa tetap terbaca dengan anon key.
- Jalankan `./supabase/011_student_selection_arrears.sql` setelah 010. Uang kegiatan/anak guru kini berlaku untuk siswa yang dicentang, dan ada input manual tagihan tahun lalu (tunggakan).
- Form siswa, Ubah SPP, kegiatan massal, anak guru, dan import CSV (bukan .xlsx) hanya untuk Admin dan ditulis ke Supabase. Login ulang sebagai Admin setelah deploy.
- Template impor siswa memuat kolom `SEKOLAH` setelah `ID`; isi nama atau kode sekolah agar siswa dengan nama sama dapat dibedakan. Template contoh memakai nama sekolah aktif.
- Impor siswa menampilkan modal pratinjau: baris bermasalah dapat diedit atau dilewati, sedangkan baris duplikat dipilih per baris. ID dari file dipertahankan: jika sudah dikenal, siswa diproses sebagai naik kelas; jika belum dikenal, sistem membuat siswa baru memakai ID yang sama. ID yang sudah terdaftar pada tahun ajaran yang sama tetap ditolak.
- Jalankan `./supabase/012_scalability.sql` setelah 011. Data dipaginasi 25 per halaman, dicari & dihitung di database (siap 5000+ siswa, 100rb transaksi), ada filter tahun ajaran.
- Pembayaran disimpan di Supabase (`spp_app_payments`) setelah migration 012; tanpa 012 hanya di browser.
- Jalankan `./supabase/013_student_edit_delete.sql` setelah 012: ubah nama siswa dan hapus massal data SPP siswa terpilih (ditolak jika masih ada pembayaran).

- Jalankan supabase/014_edit_all_fees.sql setelah 013: tombol **Ubah Tagihan** (modal) bisa mengubah DPP, DPS, Seragam, Kegiatan, SPP, dan Komputer; perubahan SPP/Komputer memakai periode berlaku.

- Jalankan supabase/015_full_billing_totals.sql setelah 014: total tagihan dashboard dan laporan mencakup SPP, Komputer, DPP, DPS, Kegiatan, Seragam, dan tunggakan tahun lalu. Daftar siswa menampilkan nominal per komponen serta riwayat transaksi secara terpisah.
- Jalankan `./supabase/016_payment_components_and_reporting.sql` setelah 015. Pembayaran baru disimpan sebagai satu atau beberapa alokasi komponen secara atomik. SPP dan Komputer bulanan otomatis dialokasikan mulai dari periode tertunggak paling lama; kelebihan pembayaran hanya dibawa ke periode berikutnya pada komponen yang sama. Pembayaran sebelum migration ini tetap berkategori `legacy`/belum dialokasikan dan tidak otomatis menutup tagihan.
- Form pembayaran menampilkan SPP dan Komputer bersama pada tiap periode. Pilihan periode mengisi nominal sesuai saldo; nominal dapat disesuaikan untuk cicilan, dan **Tambah periode berikutnya** otomatis memilih bulan selanjutnya. Periode dapat dipilih ulang secara manual.
- Jalankan `./supabase/017_payment_import_and_reporting_fix.sql` setelah 016. Migration ini memperbaiki error laporan tunggakan dan menambahkan RPC impor pembayaran yang tervalidasi serta atomik.
- Migration 016 menambahkan **Laporan Tunggakan per Kelas** dengan saldo per periode, rincian cicilan, tautan WhatsApp, dan surat yang dapat dicetak. Baris dengan pembayaran lama yang belum dialokasikan diberi peringatan dan tombol penagihannya ditahan sampai direkonsiliasi.
- Menu pembayaran mendukung impor `.xlsx`, `.xls`, dan `.csv`. Untuk Excel, aplikasi mencari lembar data berdasarkan header, melewati lembar **Contoh**/**Panduan**, dan meminta hanya satu lembar data transaksi per file. Gunakan template yang disediakan; setiap siswa, komponen, periode, dan tanggal pembayaran ditinjau sebelum diimpor. Tanggal pembayaran wajib mengikuti bukti dan tidak diganti tanggal unggah; waktu pencatatan disimpan terpisah. Periode kosong disarankan dari tunggakan terlama, dan satu file dibatasi 500 transaksi. Impor membutuhkan login Admin serta migration 017; pemeriksaan duplikat memakai daftar batch dari migration 018, dan migration 030 menegakkan tanggal wajib di database.
- Semua alur unggah pembayaran (format standar/desktop, transfer, dan crosscheck EDC/QRIS) menampilkan kesalahan per baris agar dapat dikoreksi atau dilewati. Baris yang berpotensi duplikat dari file atau transaksi yang sudah ada ditandai; operator memilih baris yang akan dilanjutkan. Header atau format file yang tidak dikenali meminta file diperbaiki dan diunggah ulang. Impor desktop tetap memakai kunci idempotensi dari migration 032.
- Dashboard pemasukan bulanan per unit serta rekap komponen tahun lalu hanya ditampilkan untuk Admin dan Yayasan. Dashboard akun Unit hanya menampilkan jumlah murid; laporan Unit tetap menampilkan nominal. RPC dashboard memeriksa role di database, bukan hanya menyembunyikan elemen UI.
- Jalankan `./supabase/018_payment_receipts_bos_and_reconciliation.sql` setelah 017. Migration ini mengelompokkan rincian menjadi satu transaksi/slip, menambah kode operator, alokasi BOS, rekap harian, dan koreksi pembatalan yang wajib beralasan. Backup data sebelum menjalankan migration.
- Jalankan `./supabase/019_two_month_billing_horizon.sql` setelah 018 untuk mengizinkan periode laporan tagihan sampai dua bulan setelah bulan aktif, dengan batas akhir Juni pada tahun ajaran yang dipilih. Periode awal pembayaran tetap mengikuti bulan masuk siswa; alokasi otomatis memilih saldo periode tertua.
- Jalankan `./supabase/020_card_print_tracking.sql` setelah 019, lalu `./supabase/021_card_print_cursor.sql`. Dialog **Cetak Kartu** menampilkan pratinjau langsung dari pembayaran yang dipilih, status cetak, dan posisi berikutnya yang tersimpan bersama per siswa, tahun ajaran, dan tabel kartu. Posisi kedua tabel dapat diatur terpisah ke baris berikutnya 1–16 melalui konfirmasi; cetakan lama tetap diarsipkan dan transaksi tersedia kembali untuk dipilih pada putaran baru. Pilihan yang sudah dicetak hanya dicetak ulang pada baris baru; setiap tabel memiliki batas 16 baris.
- Jalankan `./supabase/022_academic_year_cutoff_and_lifetime_fees.sql` setelah 021. Admin dapat menutup tahun ajaran secara manual setelah Juni; sisa SPP/Komputer berpindah satu kali ke tunggakan tahun lalu dengan rincian per periode, dan tunggakan dari tahun-tahun sebelumnya tetap terakumulasi. DPP, DPS, dan Seragam memakai saldo sepanjang masa per anak dan tidak ditagih ulang saat naik kelas.
- Untuk mencetak dengan konfirmasi printer/preview Chrome, jalankan `cetak-kartu-senyap.bat` atau buka aplikasi di Chrome biasa. Launcher tetap memakai profil cetak khusus, tetapi tidak lagi mengaktifkan mode senyap. Tutup semua jendela Chrome khusus cetak sebelum menjalankan ulang launcher agar proses lama yang masih memakai mode senyap tidak digunakan kembali; pilih printer dan periksa ukuran kertas 214 × 162 mm sebelum mencetak.
- Pembayaran manual dan impor mencetak satu slip per transaksi bergaya kuitansi: nomor dan tanggal, nama siswa dan kelas, komponen beserta periode, total terbilang, kode operator, serta ruang tanda tangan. Slip koreksi mencatat alasan dan referensi bukti asal; pembayaran tidak dihapus permanen. Data pembayaran lama ditandai `Riwayat lama` karena sumber manual/impor sebelumnya tidak tercatat.
- Tanggal uang masuk dapat berbeda dari waktu input/unggah. Layar rekap harian menampilkan ringkasan sumber manual, impor, BOS, dan riwayat lama. Laporan cetak memuat rincian per kuitansi dan siswa, dikelompokkan menurut sekolah lalu diurutkan dari kelas terkecil, dengan nominal per komponen, potongan BOS, total diterima, dan keterangan. Laporan dicetak dalam orientasi lanskap; BOS mengurangi net penerimaan orang tua. Operator mengatur kode unik melalui menu **Operator**.
- Kolom BOS tersedia pada setiap baris SPP di form pembayaran. Nominal SPP adalah total yang ditutup; setelah nominal BOS diisi, penerimaan orang tua dihitung sebagai SPP dikurangi BOS. Rincian SPP dan BOS masuk dalam satu batch dan satu slip, sedangkan dashboard pemasukan unit hanya menghitung bagian orang tua.
- Untuk satu transaksi pendaftaran siswa baru, tambahkan DPP, DPS, seragam, kegiatan, serta SPP/Komputer bulan masuk dalam satu form. Periode tagihan dimulai dari periode masuk siswa, sehingga bulan itu tidak ditagih ulang sebelum tanggal masuk.
- Tombol **Cetak Kartu** tersedia di Data Siswa dan Riwayat Pembayaran. Pilih transaksi yang telah dibayar di dialog untuk melihat pratinjau baris dan nominal sebelum mencetak; nama siswa tidak dicetak pada kartu dan SPP dicetak setelah dikurangi BOS. Posisi cetak berikutnya disimpan bersama di Supabase per siswa/tahun ajaran dan terpisah untuk tabel bulanan/nonbulanan. Reset meminta konfirmasi dan nomor baris berikutnya, sedangkan pilihan pembayaran tetap dapat diatur melalui daftar centang. Foto kartu hanya panduan layar, bukan bagian hasil cetak; siapkan kertas khusus 214 × 162 mm dan cetak pada skala 100% tanpa header/footer.
- Jalankan `./supabase/024_reporting_exports_dashboard_targets.sql` setelah 023. Migration ini menambahkan pengurutan direktori berdasarkan nama sekolah/kelas dan RPC target dashboard. Grafik memakai periode tagihan Juni–Juni: target SPP+Komputer bulanan mengikuti tarif yang berlaku, sedangkan target dan realisasi Kegiatan ditempatkan pada Juni pembuka. Unduhan Data Siswa dan Tunggakan menghasilkan `.xlsx`; ekspor tunggakan mengikuti cakupan filter dan memisahkan saldo tunggakan dari pembayaran belum dialokasikan.
- Jalankan `./supabase/025_user_management_and_hashed_passwords.sql` setelah 024. Admin dapat membuat akun, mengatur role dan sekolah, mereset password, membuka/memblokir akun, serta mengubah kode operator dari menu **Pengguna**. Password lama yang terisi dimigrasikan ke hash dan kolom password teks biasa dikosongkan; akun dengan password lama kosong perlu di-reset oleh Admin. Aplikasi lama yang membaca `mastusr.password` langsung tidak lagi dapat melakukan login. Pemblokiran menolak login dan RPC yang memvalidasi kredensial; kebijakan baca anonim yang sudah ada tidak diubah oleh migration ini.
- Jalankan `./supabase/026_fix_operator_code_result_types.sql` setelah 025 jika menu operator lama menampilkan error `structure of query does not match function result type`. Migration ini memperbaiki tipe kolom keluaran RPC operator; jangan jalankan ulang migration 018 untuk memperbaikinya.
- Jalankan `./supabase/027_annual_activity_and_provisional_students.sql` setelah 026. Migration ini membuat tagihan dan alokasi pembayaran Kegiatan per tahun ajaran, termasuk rekonstruksi pembayaran lama dari tahun tertua, serta mendukung pendaftaran siswa dengan sekolah diketahui tetapi kelas belum ditentukan. Setelah kelas dipilih, sistem membuat No. SPP final. Cadangkan database sebelum menjalankan migration; deploy aplikasi bersama migration ini. Dashboard Admin/Yayasan menampilkan ringkasan Kegiatan per tahun, sekolah, dan kelas.
- Jalankan `./supabase/028_prior_year_component_revenue.sql` setelah 027. Migration ini menambahkan rekap tagihan dan pembayaran tahun lalu untuk DPP, DPS, Seragam, Kegiatan, dan SPP, serta membuat riwayat pembayaran menampilkan seluruh periode Juli–Juni dengan area gulir tersendiri.
- Jalankan `./supabase/029_digital_payment_pending_settlement.sql` setelah 028 untuk mencatat metode EDC/QRIS serta status dan waktu settlement pada riwayat pembayaran.
- Jalankan `./supabase/030_require_payment_import_date.sql` setelah 029. Impor pembayaran menolak tanggal pembayaran kosong atau tidak valid; tanggal tidak mengikuti tanggal unggah. Template settlement memisahkan tanggal pembayaran dari tanggal dana masuk dan menyediakan contoh pada lembar terpisah.
- Jalankan `./supabase/031_payment_settlement_reconciliation.sql` setelah 030. Alur pembayaran menyediakan dua dialog settlement terpisah: **Crosscheck EDC/QRIS** untuk mencocokkan transaksi yang sudah tercatat dan **Impor Transfer** untuk mencegah duplikasi atau menautkan transfer baru ke siswa serta meninjau alokasinya. Keduanya mencari berdasarkan tanggal pembayaran (default tiga hari terakhir), hanya tersedia untuk Admin KKMS, dan memproses setiap file secara atomik. Dialog **Impor Pembayaran** umum juga memiliki template, pemilih file, dan pratinjau sendiri untuk alokasi pembayaran per siswa. Riwayat kasir dapat difilter berdasarkan rentang tanggal dan ditampilkan 10 transaksi per halaman. Tanggal settlement boleh kosong; transaksi akan tetap menunggu dana masuk.
- Jalankan `./supabase/032_legacy_desktop_payment_import.sql` setelah 031 sebelum mengimpor ekspor riwayat pembayaran desktop. File desktop memakai tanggal/periode dan komponen asal; SPP bruto dipisah menjadi bagian orang tua dan BOS, lalu nilai Kas harus cocok dengan rincian. Sistem mencocokkan ID siswa dan tahun ajaran; siswa harus memiliki pendaftaran untuk setiap tahun ajaran transaksi yang diunggah. Kunci impor per baris mencegah duplikasi saat baris lain diperbaiki, selama baris tersebut tidak berpindah posisi; transaksi tersimpan bersama tahun ajaran dan alokasi komponennya.
- Jalankan `./supabase/033_edit_student_entry_period.sql` setelah 032 agar Admin dapat mengoreksi periode masuk melalui **Ubah Tagihan**. Periode awal menentukan kapan SPP/Komputer mulai ditagih; perubahan dapat menambah tagihan dan ditolak jika melewati pembayaran bulanan yang sudah tercatat.
- Jalankan `./supabase/034_card_print_calibration_profiles.sql` setelah 033. Dialog **Cetak Kartu** memakai foto kartu kosong sebagai acuan layar saja (foto tidak ikut tercetak), menampilkan pratinjau langsung, dan menyediakan profil kalibrasi bernama yang dibagikan lewat database. Admin dapat menyimpan offset horizontal/vertikal dan skala untuk profil printer; rentang kalibrasi dibatasi agar penyesuaian tetap aman.
- Jalankan `./supabase/035_remove_ambiguous_payment_batch_overloads.sql` setelah 034. Migration ini menghapus signature lama RPC pembayaran yang bertabrakan dengan argumen metode pembayaran/settlement opsional.
- Jalankan `./supabase/036_fix_card_print_password_validation.sql` setelah 035. Migration ini memastikan RPC cetak kartu memvalidasi password menggunakan hash akun, bukan kolom password teks biasa. Jalankan juga jika migration 020 pernah dijalankan ulang setelah 025.
- `./supabase/037_reset_test_data.sql` adalah skrip reset manual, bukan migration rutin. Cadangkan database dan pastikan target adalah database tester sebelum menjalankannya; skrip ini mempertahankan data master desktop dan menjaga sequence ID siswa di atas ID master lama.
- Jalankan `./supabase/038_preserve_desktop_student_ids.sql` setelah migration 036 dan sebelum impor siswa desktop. ID yang sudah dikenal dipakai untuk pendaftaran tahun ajaran baru; ID yang belum dikenal dibuat sebagai siswa baru dengan ID file yang sama. Sequence ID otomatis diselaraskan supaya ID baru berikutnya tidak bentrok. Setelah itu, unggah pendaftaran siswa untuk setiap tahun ajaran yang diperlukan sebelum mengimpor transaksi historis.
- Jalankan `./supabase/039_student_entry_status_and_billing_check.sql` setelah 038 untuk menampilkan status pendaftaran pada daftar siswa dan memasukkan tagihan SPP/Komputer bulan masuk siswa baru ke laporan tunggakan dan dashboard pemasukan.
- Jalankan `./supabase/040_save_student_status_atomically.sql` setelah 039 untuk menyediakan penyimpanan atomik status siswa.
- Jalankan `./supabase/041_bulk_student_status.sql` setelah 040. Admin dapat memilih satu atau beberapa siswa dari kolom kiri, lalu membuka **Ubah status siswa** di toolbar Data Siswa. Status pendaftaran dapat diubah pada Tahun Ajaran yang dipilih di filter atas; periode masuk tidak berubah. Status anak guru/karyawan dapat diubah sekaligus, atau dibiarkan tanpa perubahan.
- Jalankan `./supabase/042_exclude_new_student_entry_month_spp_from_arrears_report.sql` setelah 041. Laporan tunggakan tidak memasukkan SPP dan Komputer pada bulan masuk siswa berstatus **Siswa baru**; tagihan lain tetap dilaporkan. Tagihan dan pembayaran yang sebenarnya tidak berubah.
- Filter **Kelas** pada bilah atas Data Siswa kini membatasi daftar dan jumlah siswa sesuai kelas yang dipilih.
